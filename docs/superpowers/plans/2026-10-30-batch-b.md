# Batch B Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** The owner logs a lump sum and the advisor says where it goes (one place or a split); the weekly
report lists SIP changes it saw in the feed and SIP advice when a change is due; the SIP card is capped at
the monthly budget; a warning shows when the tactical cap starts to bind.

**Architecture:** A new append-only `lump_sums` log (`/log` → "Money received") with purchases and
recommendations linkable to it, so lump-sum spending never counts against the month. A lump-sum sizer
sizes every eligible destination independently against the lump sum; a lump-sum advisor (model picks an
ordered subset of candidate ids, never amounts) runs in the weekly report job; the system allocates the
lump sum across the picks in the model's order. SIP-card logic moves from `web/lib/data.ts` into
`src/domain/sip-advice.ts` so the report job can reuse it.

**Tech Stack:** TypeScript, pnpm, vitest, PGlite (tests) / Supabase Postgres (prod), Next.js on Vercel,
GitHub Actions weekly job.

**Spec:** `docs/superpowers/specs/2026-10-30-batch-b-design.md` (owner-approved 2026-10-30). Read it
with this plan.

## Global Constraints

- Money is branded `bigint` paise (`src/money/paise.ts`); never a float. An unknown renders `unknown`/`—`, never `₹0`.
- Every new row carries `as_of` and `source`. Owner-logged rows use `source = 'owner-web'`.
- New log tables: append-only triggers (UPDATE, DELETE, TRUNCATE via `sentinel_append_only()`) + RLS on with no policy, as `migrations/0039_sip_moves.sql`. Reversal only through `log_reversals`.
- Never pass `JSON.stringify(x)` to a `::jsonb` parameter for new code paths that prod reads back; read jsonb through `instrumentMeta(alias)` / `auditPayload(alias)` (MEMORY.md gotcha). `recordProposal` already stringifies — read proposals only through `loadProposals`, which parses.
- `src/advisor/` writes only advisor tables (`tests/advisor/firewall.test.ts`). The model never states an amount; sizes are the system's.
- Nothing here reads goal status (`tests/architecture/no-catch-up.test.ts`).
- The advisor invests for the long term (CLAUDE.md): HOLD/WAIT ("keep it in the bank for now") are valid answers; no action is justified by short-term price movement.
- Backend and UI ship together: getter in `web/lib/data.ts`, page, `web/lib/product.ts` row honest `works`/`missing`. UI from `web/lib/ui.tsx` primitives.
- `Db` interface: `query`, `exec`, `withTransaction` (does not nest), `close` — see `.superpowers/sdd/2026-10-29-fund-switch/db-contract.md`.
- Subagents run on Opus.

## Review Focus

1. **A reversed lump sum** — its linked purchases count against the month again, it gets no further advice, and its open-advice block disappears. Test in Task 1 (`reversal returns linked purchases to the month`) and Task 6 (`a reversed lump sum cannot be signed`).
2. **A purchase larger than what is left of the lump sum** — refused with the amount left named. Task 1 test.
3. **A one-unit price above a part's allocation** (gold ETF, stock) — that part is dropped and its money flows to the next pick; never a fractional unit, never a ₹0 part. Task 4 test.
4. **SIP feed stale or unknown at report time** — the SIP-change and SIP-advice lines say the feed is stale/unknown; they never say "no change". Task 3 test.
5. **Current SIPs already at or above the budget** — the card suggests no increase and says why; it never cuts. Task 2 test.

- Produces:
  - `loadFundCandidates(db, asOf, opts?: { upToMax?: boolean })` — with `upToMax`, a held top-uppable fund is a buy while its type's share is **below the range max** (not midpoint); every other exclusion unchanged.
  - `export interface LumpSizingInput { lumpSumId: string; remainingPaise: bigint; sizing: SizingInput; fundTotalPaise: bigint; newFunds: { instrumentId: string; name: string; fundType: FundType; why: string }[]; gold: { instrumentId: string; name: string; kind: string; actualBps: number; maxBps: number; portfolioPaise: bigint } | null }`

  - `allocateLumpSum(candidates: Candidate[], chosenIds: string[], remainingPaise: bigint): { candidate: Candidate; amountPaise: bigint; units: string | null }[]` — pure.
  - `loadSizingInput` adds `openLumpSumPaise(db)` to `reservedPaise` (the monthly plan never spends lump-sum money).

**Rules:**
- Each candidate is sized **independently** with ceiling `min(remaining, maxOrder, cash − reserved − other open lumps, headroom)`; no tranche is shared between candidates. Headroom: held fund → `(maxBps − actualBps) × fundTotal / 10 000`; new fund → `(maxBps − actualBps of its type) × fundTotal / 10 000`; gold → `(IPS_BANDS.GOLD.max − actual) × portfolio`; stock → single-stock-cap headroom, and stocks wait exactly as in `sizeCandidates` (`stocksWait`). Single-scheme cap (35%) still withholds.
- New funds: the switch check's `units.kind === 'move'` targets (`toId`) whose type takes new money, and `chooseIndexFund(...).top` for every index type with no held fund (`MFU:<amfiSchemeCode>`). `registerIndexChallengers` registers each type's top and alternatives even when no fund of that index type is held (category = the AMFI category of the ranked row).
- Gold: the held GOLD-kind exchange-traded instrument with the largest value; null when none is held or GOLD is at or above its band max.
- `allocateLumpSum`: walk `chosenIds` in order (unknown or WITHHELD ids skipped); each part `min(candidate.amountPaise, left)`; exchange-traded parts floor to whole units at `pricePaise`, and a part with 0 units is dropped (its money stays for the next pick); stop when `left = 0`. Never a ₹0 part.

Two failed attempts → `UNAVAILABLE`, never HOLD. No ELIGIBLE candidate → `NO_ACTION`, no call.
- BUY payload `parts` = `allocate(candidateIds)`; an empty allocation → decision `WAIT` with reason `no pick could be bought with the amount left`.
- When to run (`lumpSumAdvice`, every weekly report, independent of the monthly budget hold): for each open lump sum, skip if its latest LUMP_SUM proposal is OPEN, or SIGNED as BUY; re-advise if there is none, the latest is DISMISSED, or the latest was a HOLD/WAIT/NO_ACTION/UNAVAILABLE older than 28 days. Line: `Lump sum ₹<remaining> (<from>): <decision>. Review it on the Advisor page.`
