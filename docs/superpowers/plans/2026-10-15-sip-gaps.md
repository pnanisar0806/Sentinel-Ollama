# SIP gaps Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: superpowers:subagent-driven-development. Steps use checkbox (`- [ ]`) syntax.

**Goal:** The free amount for the month is honest. A SIP stopped after this month's instalment still counts. A purchase the owner made outside Sentinel, and logged on `/log`, counts against the month. The app shows and enforces **remaining to invest**.

**Architecture:**
- `src/domain/sips.ts` stays the single home of month money: commitment, envelope, spend and remaining.
- The owner logs outside purchases into a new append-only `owner_purchases` table through `/log`.
- Every consumer of the envelope (sizing, the order gate, the rebalance tranche, the advisor block and the web) moves from `envelopePaise` to `remainingPaise`.

**Tech Stack:** TypeScript, vitest + PGlite, postgres-js/Supabase, Next.js `web/`.

**Spec:** the owner-approved design in chat, 2026-10-15. It is recorded in the ledger `.superpowers/sdd/2026-10-15-sip-gaps/progress.md`. Context: `docs/superpowers/specs/2026-10-14-sips-goals-advisor-design.md` §1 and MEMORY.md "Owner decisions 2026-10-13/14" plus the free-envelope contract.

## Global Constraints

- Money is never a float: branded `bigint` paise only. Rupee text converts exactly, as `web/app/api/log/route.ts` `paise()` already does.
- Every row from an external source or from the owner carries `as_of` and `source`. Owner rows use `source = 'owner-web'`.
- An unknown is `NULL`, never `0`. It renders as `unknown` or `—`, never `₹0`.
- Every new table is append-only. UPDATE, DELETE and TRUNCATE are refused by `sentinel_append_only()` triggers, and RLS is enabled.
- **"This month" means the Asia/Kolkata calendar month** in all new code. The existing order-spend query (`getTacticalUsedThisMonth`, `to_char(o.as_of,'YYYY-MM')`) is UTC. Move it to IST in this plan so spend and SIPs use one month definition.
- `remainingPaise = max(0, envelopePaise − spentPaise)` where:
  - `envelopePaise = max(0, min(tactical, budget − sipCommitment))`, as today;
  - `spentPaise` = this month's open or executed Sentinel BUY orders (today's `getTacticalUsedThisMonth` semantics) **plus** this month's `owner_purchases`.
  - SIP instalments are **not** added to `spentPaise`. They are already inside the commitment. Never count them twice.
- An unknown envelope means unknown remaining. Every BUY is withheld, and the month is not consumed. These are the existing owner decisions and are unchanged.
- No module may import `src/domain/buckets.ts` or `src/domain/funded-status.ts`.
- Never widen a test band or edit an expected constant to make a red test green. Derive expected values from fixture rows.
- The `Db` interface is `{ query<T>(sql, params?): Promise<T[]>; exec(sql); withTransaction<T>(fn); close() }`. PGlite returns `date`/`timestamptz` as `Date` and postgres-js returns strings, so select `::text` where exactness matters.
- Commit locally only. Never push. Messages end with `Co-Authored-By: Claude Opus 5.5 (1M context) <noreply@anthropic.com>`.

## Review Focus

1. **A purchase logged with a date in a previous month** must not reduce this month's remaining amount.
2. **A Sentinel-proposed order** is counted once. It lives only in `order_intents`. The `/log` purchase form says it is for purchases made outside Sentinel.
3. **A SIP seen this month before its instalment day, then gone,** was not debited this month. It must not count (Task 1).
4. **The first month** a newly registered SIP appears with a start date in the future (e.g. Invesco, start 2026-11-12, seen on 2026-10-20). It counts toward the commitment from the snapshot it appears in, exactly as active SIPs do today. Do not add special-casing.
5. **Logged purchases greater than the envelope:** remaining is 0, and nothing negative appears anywhere.

### Task 1: SIPs stopped after this month's instalment still count

**Files:** modify `src/domain/sips.ts`, `tests/domain/sips.test.ts`.

**Interfaces:**
- `SipCommitment` gains `departedThisMonth: ActiveSip[]`. These are SIPs that are absent from the latest snapshot but still count for the current month.
- `totalPaise` = active SIPs + departed SIPs. It is null under the same conditions as today.

**Rule.** The current month is the IST month of `nowIso`. A SIP id that is absent from the latest snapshot is **departed-this-month** if both of these hold:
- some earlier snapshot whose `as_of` falls in the current IST month contains it;
- in the latest such snapshot that contains it, the IST date of that snapshot's `as_of` is on or after that SIP's instalment day this month.

The instalment day is the day-of-month of its `start_date`, clamped to the month's length.

Use that last-seen row's amount. A SIP last seen *before* its instalment day was not debited this month and does not count (Review Focus 3).

- [ ] **Tests, red first:**
  - **Counts when last seen after its instalment day:** a SIP is in a snapshot on 2026-10-14 (instalment day 12) and absent from the 2026-10-20 snapshot. It counts in October. In November it does not.
  - **Does not count when last seen before its instalment day:** a SIP is last seen 2026-10-05 (instalment day 12) and is gone on the 2026-10-20 snapshot. It does not count.
  - **Previous month does not count:** a SIP last seen in September does not count in October.
  - **No double counting:** an active SIP that is also in earlier snapshots counts once.
  - **Day clamping:** a 31st instalment day in a 30-day month clamps to the 30th.
  - **Staleness:** a stale latest snapshot makes the total null even when departed SIPs exist.
  - **Mutation check:** treat every departed SIP as counted. The before-instalment test must go red.
- [ ] Implement. Keep `loadFreeEnvelope` unchanged apart from receiving the new total.
- [ ] Run `pnpm vitest run tests/domain/sips.test.ts tests/domain tests/architecture`, then the full suite once, then `pnpm exec tsc --noEmit`. Commit locally.

**Table.**

```sql
create table owner_purchases (
  id bigserial primary key,
  bought_on date not null,
  instrument_id text,            -- optional link; null when the owner names a fund that is not an instrument
  description text not null,     -- what the owner typed, e.g. "Zerodha Gold ETF"
  amount_paise bigint not null check (amount_paise > 0),
  units numeric check (units is null or units > 0),
  note text not null default '',
  as_of timestamptz not null,
  source text not null default 'owner-web'
);
```

Add the append-only triggers and RLS, using the same do-block pattern as `0032_sips.sql`.

**`logPurchase(db, p, now)`:**
- Validates: amount > 0; date not in the future (reuse `assertDate`); description non-empty and ≤ 200 chars.
- Inserts the row and an `audit_log` row (`entity 'owner_purchase'`, action `'LOGGED'`, actor `'owner'`) in one transaction.
- The timeline shows "Bought ₹X of <description>".

**Interfaces:**
- `loadMonthSpend(db, nowIso)` returns `{ ordersPaise, ownerPaise, totalPaise }` for the current IST month.
- `FreeEnvelope` gains:
  - `spentPaise: bigint`, always known: a sum of rows, 0n when there are none;
  - `remainingPaise: bigint | null`, which is null iff `envelopePaise` is null.
- When `remainingPaise` is 0 because of spend, the reason is "this month's budget is already deployed (₹X spent)".

  - Sizing offers at most the remaining amount.
